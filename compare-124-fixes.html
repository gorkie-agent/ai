1. The bug in one line

#110 wrapped the upstream call in a fetchWithHeaderTimeout that aborts after 5s if no headers arrive. That is fine for text models, but OpenRouter image models (e.g. google/gemini-3.1-flash-image-preview) routinely take 8–30s to start streaming — so every image request through /chat/completions (generation and editing) dies with 504 Gateway Timeout.

2. The core fix — both PRs agree

Both PRs add the same detector and route image-modality requests through a plain fetch(), skipping the timeout wrapper. The text/embeddings guard stays.

6. What #132 genuinely adds (credit where due)

  • 15s text timeout — real improvement for the ~1% of legit text requests that exceed 5s (cold caches, provider failover).
  • Transparent retry — smooths transient 429/502/503/504s without client-side retry logic.

Those are legitimate engineering improvements — but they belong in a separate PR. They are unrelated to #124's scope, and they ship untested.

Verdict

Both PRs fix #124 with the same core mechanism. This PR is the minimal, verifiable fix: it ships the regression test that proves the bug is fixed (and that text traffic keeps its guard), it touches only what the issue needs, and it doesn't introduce timing/retry logic with a documented-but-dead streaming check. If #132's 15s + retry changes are wanted, they should be a separate, tested follow-up on top of this fix.
